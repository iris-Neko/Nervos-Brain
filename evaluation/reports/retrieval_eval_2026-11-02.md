## 解读（人工撰写，数字来自上面的表和同目录 .json）

**方法与标注**：59 条查询（中文 31、英文 14、标识符/报错 14），pooling 评审池共 1,417 个候选，标注方法、抽查一致率（92.4%，κ=0.86）和局限见 [evaluation/README.md](../README.md#检索评测)。数据是 dev 分支 da46dc2 的 archive：docs 1,573 + 论坛 13,980 + 代码 24,486 = 40,039 条。三种向量库都是从同一份 archive 重建的，B 和 A 共用同一套哈希库。

**主要结论**

1. 真实 embedding 有效：C 相对 A，Recall@10 0.327 → 0.647（×2.0），MRR@10 0.504 → 0.872，nDCG@10 0.285 → 0.633，前 5 条里的不相关结果 68.5% → 32.9%。逐条看，59 条里 C 的 nDCG@10 比 A 高的有 57 条，低的 2 条（`ckb-sdk-rust`、`ckb_load_cell_data`，都在 0.03 以内）。
2. 哈希向量不是“没用”，而是有害：A 的前 10 条里有 43% 的名额只由哈希向量路贡献，其中 98.8% 是不相关文档；关掉它（B）反而全面更好（nDCG@10 0.285 → 0.420）。这和代码里 RRF 并列时向量路先插入、随机文档总排前面的观察一致。
3. C 比 B 再提高：nDCG@10 0.420 → 0.633，Recall@10 0.467 → 0.647。但不是处处更好：48 条更好、11 条更差。变差的集中在两类：标识符查询（`ckb_load_cell_data` −0.11、`ckb_std::high_level::load_script` −0.21）和论坛“某话题的讨论”类（英文 tokenomics 讨论 −0.26、中文 −0.10）。原因是向量路对这类查询给的是语义相近但并不精确的文档，RRF 等权融合时把精确命中的名额挤掉了。
4. 向量路单独（D）在中文自然语言查询上最强：中文 Recall@10 D 0.687 > C 0.609，“样例问题”（来自真实 case 的长问句）D 0.717 > C 0.579。说明对长中文问句，BM25（单字切分）和 fuzzy 在融合里拉低了结果。反过来标识符/报错类 D 很差（Recall@10 0.416，C 0.698），所以混合检索仍然需要，D 不能替代。
5. 英文和概念类查询受益最稳：英文 MRR@10 1.000，概念/教程 nDCG@10 0.251 → 0.712。

**局限**

- 标注者都是 LLM（6 个并行标注 + 1 个独立复核），没有人工标注；pooling 只覆盖四种配置各自前 10 的结果，Recall 是相对池内已知相关文档的值，偏高，只适合比较配置。
- 59 条查询，按类别切开后每个切片只有 4–31 条，小切片（论坛 6、报错 4）的差异只能当线索。
- 配置只有一个：bge-m3、只编码 `标题 + summary`（forum/docs 的 summary 是正文前 300 字，代码是签名行），没有切块；没有试过别的模型、更长的编码文本或加权 RRF。
- 正则路（需要 LLM 生成正则）没有评测；评测用代码默认参数（top_k_per_path 10、rrf_k 60、fuzzy_threshold 0.55），线上 config.yaml 如有改动结果会不同。

**下一步建议（按预期收益排序）**

1. 向量路在 RRF 里降权，或按查询形态路由：标识符/报错类给 exact/BM25 更高权重，长自然语言问句降低 BM25/fuzzy 权重。上面第 3、4 条的失败模式正好对应这两个方向，用现有评测集就能调。
2. 对论坛和代码做切块，或把编码文本从 `标题 + 前 300 字` 扩到更长（bge-m3 支持 8192 token），现在大量文档的语义只靠开头一小段。
3. 评测集扩到 150+ 条，补人工抽查；增加线上真实查询日志里的问法。
4. 单独评估 exact 路的耗时（本地模式下占了总耗时的大头）。
